# Performance Test Instructions

## Purpose and scope

요구사항의 규모는 **소규모: 매장당 최대 약 20개 테이블**, 단일 프로세스, 로컬 실행입니다. 명시된 성능 요구는 "신규 주문이 관리자 화면에 2초 이내 전달"입니다. 따라서 대규모 부하/스트레스 시험은 범위 밖이고, 소규모 동시 사용에서 오류·이벤트 누락·지연이 없는지 확인하는 가벼운 시험만 제공합니다.

## 목표

| 항목 | 목표 |
|---|---|
| 신규 주문 → 관리자 SSE 수신 | 2초 이내 (요구사항) |
| 20개 테이블 동시 주문 | 오류 0건, 이벤트 누락 0건 |
| 주문 응답 시간 | 정상 사용(테이블 20개가 동시에 쉬지 않고 주문하는 상황보다 훨씬 가벼움)에서 체감 지연 없음. 아래 측정값을 기준선으로 기록 |

## 시험 실행

```powershell
cd backend
python scripts/seed.py
python -m uvicorn app.main:create_app --factory --port 8000 --timeout-graceful-shutdown 5   # 별도 터미널
python scripts/load_smoke.py http://127.0.0.1:8000 --tables 20 --orders 10 --subscribers 5
```

- `--tables N`: 테이블 1..N을 (없으면) 등록하고 각각 별도 스레드에서 동시에 시작
- `--orders M`: 테이블당 연속 주문 수 (응답을 받자마자 다음 주문, 즉 현실보다 훨씬 거센 부하)
- `--subscribers K`: 관리자 SSE 구독자 수
- 기본 자격 증명이 다르면 `LOAD_STORE_ID`, `LOAD_ADMIN_USER`, `LOAD_ADMIN_PASSWORD` 환경변수를 설정
- 대상 DB에 테이블/주문이 쌓이므로 개발용 DB에서만 실행하세요. 끝난 뒤 `python scripts/seed.py --reset --yes` 로 초기화할 수 있습니다.

출력: 성공(201) 건수와 처리량, 응답 시간 p50/p95/max, 오류 상태 코드별 건수, 이벤트 누락 건수, 이벤트 전달 지연(응답 완료 후) p95/max, 최종 "통과/확인 필요".

## 측정 기준선 (검증 환경, 2026-10-14)

환경: Windows 로컬, 단일 uvicorn 프로세스, `BCRYPT_ROUNDS` 기본(12), 임시 SQLite 파일, 20 테이블 x 10건 = 200건 동시, SSE 구독자 5명.

| 항목 | 결과 |
|---|---|
| 요청/성공 | 200 / 200 (201), 오류 0건 |
| 처리량 | 약 17.6건/초 (11.4초) |
| 주문 응답 시간 | p50 47 ms, p95 약 1.2초, max 약 2.4초 |
| 이벤트 | 5명 x 200건 = 1,000건 중 누락 0건, 응답 완료 시점 이전에 도착(지연 0 ms로 계산) |

해석과 한계:
- 이벤트 전달은 요구사항(2초 이내)을 충족하고 누락이 없었습니다.
- 응답 시간의 꼬리(p95/max)는 20개 클라이언트가 쉬지 않고 연달아 요청하는 가혹한 조건에서 SQLite 쓰기 직렬화(`BEGIN IMMEDIATE`)와 대기 때문에 늘어난 것으로 보입니다. 원인은 프로파일링으로 확정하지 않았습니다. 실제 매장은 테이블 20개가 몇 초에 한 번 주문하는 수준이므로 훨씬 가볍습니다.
- 한 대의 PC, 단일 프로세스 한 번의 측정입니다. 통계적 성능 보증이 아닙니다.

## 병목이 의심될 때

1. 같은 시험을 `--orders 3` 등으로 줄여 꼬리 지연이 부하에 비례하는지 확인
2. `BCRYPT_ROUNDS` 영향 배제: 로그인(해시 검증)은 시험의 측정 구간 밖이며 주문 요청에는 해시 연산이 없음
3. 서버 로그(stderr)에 오류가 없는지, DB 파일이 느린 디스크/동기화 폴더(OneDrive 등)에 있지 않은지 확인 (`DB_PATH`)
4. 여러 워커를 띄우면 EventBroker가 프로세스 메모리에 있어 이벤트가 구독자에게 가지 않으므로 사용하지 않습니다 (단일 프로세스 유지)
